## (a) Requirements asked for that are missing or partial

- **[M] [HARD] ADR-0018 §6 / #197 (f): "a persisted Armed / Fired (a crash) runs one clear-all" — src/ProsimCompanion.Speech/Scenarios/ScenarioService.cs:209-213 runs `ClearAllAsync("startup")` from `Start()`, i.e. inside `StartupModuleHost.StartAsync`, before `ProsimConnectionService.RunSessionsAsync` has set `_connection` (src/ProsimCompanion.Prosim/ProsimConnectionService.cs:202). `SdkFailureInjector.RunAsync` then answers "no SDK session" (-1), the STATUS row reads "could not clear — check the IOS", and nothing retries on the connected edge. The ADR's stated fallback (say it on the STATUS page and in the log) is met, but the intent — a crash never leaves a stale failure armed — is not: in practice the one clear-all never reaches ProSim.
- **[M] [JUDGEMENT] #197 (d) "at the first live Preflight of a flight cycle, roll `scenario.perFlightChance`" — ScenarioService.cs:280-283 calls `TryPlan` only on the Preflight phase edge, and TryPlan (:293) returns without planning when `!_flight.IsLive`. Nothing re-tries once the flight becomes live, so a Preflight edge that lands before the live gate (a restart at the gate, the restored Unknown→Preflight edge) means that flight is never planned — silently, with no log line. "First *live* Preflight" reads as "the first Preflight tick that is live", not "the Preflight edge, if live". Unverified on the rig; the ordering of the restore edge and the live gate is the question.
- **[L] [HARD] #197 (c) "a scenario the FO cannot respond to is refused at load and named on the Config page" — ScenarioService.cs:321-327 `Known()` logs a Warning and skips the entry; no `ConfigProblemStore.Report` anywhere (the service does not take the store; `ScenarioCatalogueBank` reports parse problems only). The Config page never names the bad `abnormalId`.
- **[M] [JUDGEMENT] #205 "While a checklist line is pending, its answer should win over the minimums read-back (or the read-back should also satisfy the line)" — the fix is seed data only (src/ProsimCompanion.App/config/checklists/descent.json: "Minimum" now accepts "minimums", "decision altitude", …). The router already tries the checklist answer first (src/ProsimCompanion.Speech/Recognition/UtteranceRouter.cs:556) and `IsAccepted` is a whole-word contains match (src/ProsimCompanion.Speech/Checklists/SpokenChecklistEngine.cs:780-787), so "minimums one eight seven" now lands on the line — but a bare "one eight seven" (the leg-one record only says `said '187'`) still fails acceptance and falls through to the read-back feature at :611-618, exactly the reported sequence. Neither "the line wins" nor "the read-back also satisfies the line" is implemented as a rule.
- **[M] [JUDGEMENT] #107/#205/#193 seeded-checklist fixes ride ADR-0007 keep-user-edits** — the three changed files (taxi.json, approach.json, descent.json) are seed source only; a user-edited copy under `%LOCALAPPDATA%` keeps its text. #193's own write-up says the owner's taxi.json on the sim PC is user-edited, so the V-speeds "set / checked" and Briefing "completed" answers (taxi.json) will not reach the rig that reported them. The changelog line does not say so.
- **[L] [JUDGEMENT] #198 "One reminder after `transitionReminderDelaySeconds` (30) if the side has not changed" and the acceptance "the one re-ask" — src/ProsimCompanion.Speech/Callouts/TransitionReminderCore.cs:98,116 latch `_standardSpoken` / `_qnhSpoken` after the single delayed line; there is no second ask. Readable either way ("one reminder" vs "re-ask"); flagged, not failed.
- **[L] [JUDGEMENT] #197 (e) "At shutdown the existing post-abnormal tech-log offer fires with `techLogAfter` as the title (an override title per abnormal id)" — `TechLogAfter` is carried on `ScenarioEntry`/`ScenarioPlan` but nothing outside `Scenarios/` reads it (grep: zero references in Speech/TechLog). The shutdown offer uses its own title.

## (c) Implemented but looks wrong

- **[M] [HARD] ADR-0018 §4 "Never in flight below `scenario.minAltitudeFt` AGL … never in a sterile moment" — the floor has a hole on the runway.** src/ProsimCompanion.Core/Scenarios/ScenarioScheduler.cs:209 applies the AGL floor only when `tick.Phase` is InitialClimb/Climb/Cruise/Descent/Approach; `tick.Sterile` (:231) is the arbiter's rule, which is false in TakeoffRoll and LandingRollout by design (SpeechSuppression.cs:117-123). A non-takeoff entry whose user-editable `phases` lists `TakeoffRoll` or `LandingRollout` (scenarios.json is a user file, ADR-0018 §5) therefore arms instantly on the roll with no floor and no sterile hold; the manual `scenario.arm` path (ScenarioService.cs:760 `Phase = _flight.CurrentPhase`, :775 `PhaseSinceUtc = Now().AddHours(-1)`) reaches the same branch from the API in any phase. The ADR's own carve-out for the roll is the two takeoff scenarios "on the SDK's own after-V1 / takeoff condition", not an immediate `ArmedFailure.Create`.
- **[M] [JUDGEMENT] ADR-0018 §5 "entries name … `phases` allowed" — the manual arm ignores them.** ScenarioService.cs:747-790 builds the plan with `Phase = _flight.CurrentPhase` and never checks `entry.Phases`, so `scenario.arm brakes-hot` (catalogue: TaxiIn only) arms in the cruise. `Allowed()` only checks Verified/Weight/Severity/Takeoff.
- **[S] [JUDGEMENT, unverified] ADR-0018 §3 "write → verify" may never verify.** The verify loop (ScenarioService.cs:471-490) looks for its handle in `ArmedAsync`, which recovers the handle by `ReferenceEquals(pair.Value, item)` over `getArmedFailures()` (src/ProsimCompanion.Prosim/Failures/SdkFailureInjector.cs:101). If the SDK materialises fresh `ArmedFailure` wrappers per call (the ADR's own consequence section says "a rebuilt session invalidates every SDK object"), no item is ever reference-equal to the one `Create` returned, every arm reads "not-verified" and is cleared 5 s later — scenario mode would be dead on the rig with a clean log. Needs one live check; a name-based fallback (`FirstName(item) == plan.FailureName`) would close it.
- **[L] [JUDGEMENT, unverified] #197 (a) "`rto-cause` (eng fire at 80–100 kt)"** — ScenarioService.cs:461 maps every non-EFATO takeoff entry to `FailureAfterEvent.Takeoff` with delay 0. Whether ProSim's `Takeoff` event means thrust-set (fire at 0 kt, a trivial RTO) or liftoff (no RTO at all) is a rig fact; neither is "80–100 kt".
- **[L] [JUDGEMENT] #194 "random, never the previous day's FO" — `FoRosterDraw.Pick` (src/ProsimCompanion.Core/Persona/FoRosterDraw.cs) is correct; but the issue's trigger "with day mode off, the first Preflight of a session on a new sim calendar day" was narrowed by ADR-0019 §8 to "one FO per sim calendar day, never per day id" (FoRosterTriggerCore.cs). This is an owner decision, so not a defect — recorded so the #194 acceptance line is read against the ADR, not the issue.
