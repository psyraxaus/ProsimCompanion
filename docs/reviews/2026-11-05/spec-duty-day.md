Fixed point `main` = 0db90771, HEAD = ee2c2ef0. Commits read: 7f56c58b, a03094a8, 9cbd82bc, 6724259e, 3ce3e5a6, fccd2163, 17a9c2c8, d7f3ee73, e5d86287, plus the owner-answer commit 619949b9. Issues #207–#223 read via the GitHub MCP (no comments on any of them). Every finding below was traced in the file named; "unverified" marks the one I could not prove without the sim.

**Headline.** The ADR is implemented almost section for section: all ten numbered sections have code behind them, all five owner answers of 619949b9 are in the ADR text *and* in code, all 14 silent misses and all 7 wrong displays have a fix I can point at, the two ADR defaults (Duty Day on, backstop 300) are the class defaults and therefore the settings-page defaults (the page is `[OptionField]`-driven; `DayOptions.cs:20,36`; hint text `lang/en/speechSettings.json` "autoClose.hint" in all seven packs; manual row `docs/manual/04-settings-reference.md:51`). The replay re-derives Deboarding Completed (`FlightReplay.cs:213-219`, expected file ends `Shutdown -> Preflight`). What is wrong sits at the edges: the end-of-duty path and the restart path each leave one latch behind, and one ADR button is missing.

## (a) Requirements missing or partial

- **[HARD] [M]** ADR §8 *"the web button (Flight Status and Duty Day cards)"*; #217 repeats it — only the Duty Day page has the button (`src/ProsimCompanion.Web/Pages/Day.razor:121,211`). `Home.razor` has no day control at all (`grep IDayControl src/ProsimCompanion.Web` → `Day.razor` only; `grep -i day Home.razor` → nothing). The Flight Status card got the leg chip (`Home.razor:120-125`) but not the end-of-duty button the ADR names beside it.
- **[JUDGEMENT] [M]** ADR §8 *"The roster draws one FO per sim calendar day, never per day id and never mid-day"*; #219 *"an open duty day pins its FO until end of duty"* — `src/ProsimCompanion.Core/Persona/FoRosterTriggerCore.cs:75` `var dayPinsFo = inputs.OpenDayLegsCompleted is > 0 && inputs.HasCurrent;` pins only once a leg has landed. An open day on leg 1 (auto-started at Preflight, plan loaded, not yet pushed) that is restarted after the sim date rolls over hits the `InPreflight && LegPlanned` opportunity (`:74`) with a different stamp and redraws — mid-day by the issue's definition. The recorded EHAM case (leg 1 flown) is covered; the day-one case is not.
- **[JUDGEMENT] [L]** ADR §8 *"the day record closed (logbook and fuel log final)"* — `CompanyDayService.cs:730` folds the logbook; nothing on the fuel-log side subscribes to `DutyDaySignals.DayEnded` (subscribers: `FlightStateSnapshotService.cs:204`, `LegBoundaryService.cs:96`, `GsxAutomationService.cs:191`). Unverified whether the fuel log has anything to finalise per day; if not, the ADR sentence is the thing to trim.
- **[JUDGEMENT] [L]** ADR §2 *"while parked with the engines off"* — `src/ProsimCompanion.Core/Flight/LegBoundaryService.cs:217` demands `data is { IsValid: true, OnGround: true, AnyEngineRunning: false }`. With SimConnect down and ProSim up (a degraded start, which CLAUDE.md says must stay usable) an IOS Reset FMS is recorded `accepted: false` and the chip never leaves TURNAROUND; the phase engine's own ColdAndDark/Preflight would do as a fallback witness.

## (c) Implemented but wrong

- **[JUDGEMENT] [S]** ADR §8 *"A plan loaded after the end starts a new duty day"*, §1 *"not when the aircraft is powered"*, §5 *"a leg row exists only once its OFP does"* — `src/ProsimCompanion.Speech/Day/CompanyDayService.cs:496` `autoStart = current == FlightPhase.Preflight && options.Enabled && options.AutoStart;` runs whenever `day is null || !day.IsOpen` — an *ended* day is `!IsOpen`. So after "end duty day" at the gate, the next ColdAndDark → Preflight edge (power cycle, next sim morning before the OFP is fetched) calls `TryStartDay("auto")` (`:528`), and `:682` seeds leg 1 from `_ofp.Current` — the flown plan still in the store (or re-imported from the EFB at start). The day page then reads "Leg 1 EHAM → EGLL" until the real OFP re-seeds it. The ADR wants the OFP, not the Preflight edge, to open a day after an end of duty; `HandleLegBegan:350` already does that — the Preflight auto-start should be limited to "no day has ever existed this session" (or `_engine.Day is null`).
- **[JUDGEMENT] [M]** ADR §2 *"The same OFP loaded twice is one leg: nothing resets"* and §8 (above) — `LegBoundaryService.cs:195` `_core.Restore(LegBoundarySnapshot.Empty with {...})` on `DayEnded` drops `PlanId`, whereas `Airborne` (`LegBoundary.cs:184`) and the GSX side (`GsxAutomationService.cs:211` keeps `_lastResetPlanId` as the baseline) deliberately keep it. `OfpStore.Set` raises `Changed` unconditionally (`OfpData.cs:224-232`), so a forced re-import of the *flown* plan after end of duty (Fetch OFP before the new plan exists) makes `PlanLoaded` read "first plan of the session" → `LegBegan` → a new duty day auto-starts on the flown plan, the FMGC cross-check re-arms (`FmgcCrossCheckService.cs:166`) and the purser's cabin-empty latch resets. Keep the id, clear only the state and flags.
- **[JUDGEMENT] [M]** ADR §6 *"resets everything the arrival resets … when boarding has not started"* — `src/ProsimCompanion.Gsx/Automation/NewPlanCycleReset.cs:57` `return cycleComplete || !boardingObserved;`. A regenerated SimBrief OFP (new request id — the normal result of "Generate" after a fuel change) with boarding completed and the cycle closed still resets the departure side *and* raises `FlightCycleReset(NewPlan)`: pax target, notification latches, gate monitor, walkaround, loadsheet editions — on a boarded aircraft. Inherited from #207's wording ("never while … under way"); the ADR's bar is boarding, full stop.
- **[JUDGEMENT] [S] (unverified live)** ADR §9 *"A restart is invisible"* with #221 — `src/ProsimCompanion.Speech/FoSide/FmgcCrossCheckService.cs:55` `private bool _armed = true;` is never derived from the restored `LegBoundaryStore`. A restart inside TURNAROUND (snapshot restored, flown plan still in the box, V1 still entered — the state restarts 2/3 at EHAM were in) starts armed, `AutoDue` is satisfied in Preflight at the gate, and "INIT page: EGLL to EHAM" is spoken again — the B3 symptom by another door. `ArrivalCompleted` disarms it only when this process sees the edge. Fix: start disarmed when the boundary store is already Turnaround/AwaitingPlan.
- **[JUDGEMENT] [L]** `LegBoundaryService` constructor (`:79-88`) feeds `PlanLoaded` from whatever the OFP store holds at construction, before the snapshot restore (`RestoreOrder 5`). If the EFB re-import lands first with the flown plan this is fine (same id); if it lands first with a *new* plan the turnaround part is still restored on top (`Restore:147` overwrites the PlanId with the flown one) and the new plan never fires `LegBegan`. `FlightStateSnapshotRules` guards the whole-document case (`currentRequestId` → Discard) but `boundaryOnly` documents skip that check unless a request id is held — so this only bites when the plan arrives between the identity check and the part restore. Timing window; noted, not proven.
